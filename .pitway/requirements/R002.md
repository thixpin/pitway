# PitWay — Add a Backlog / Deferred Work Milestone

Start a **new milestone** for PitWay to introduce a first-class workflow for capturing work discovered during execution that is intentionally deferred to a later time.

## Objective

When working on a milestone/task, a developer or AI agent may discover an unrelated issue, improvement, technical debt, or follow-up work that should **not** be implemented within the current task or milestone.

PitWay should provide a controlled way to record that work as **deferred backlog work**, preserving enough context to understand where and why it was discovered.

The goal is:

> Discover → capture → defer → continue current work → later promote into planned work.

This must reinforce PitWay's existing scope-control philosophy rather than becoming a general-purpose issue tracker.

## Core Requirement

Introduce a structured **Backlog / Deferred Work** concept. A backlog item represents work discovered during an existing workflow that is intentionally deferred. The backlog item must not silently become part of the current task or milestone.

## Scope Control Principle

The most important invariant is: discovering deferred work must never expand the scope of the current task or milestone. A backlog item must therefore be independently identifiable and traceable.

## CLI Surface

`pitway backlog add|list|show|promote|archive`, following existing PitWay CLI conventions.

## Backlog Item

Minimum fields: stable backlog id, title, description/reason, source milestone/task, status, creation timestamp, promotion metadata. Avoid redundant information derivable from existing state.

## Traceability, Journal Integration, Promotion

Backlog mutations must follow the existing journal/state architecture with explicit events for created/promoted/archived. Promotion links a backlog item to real planned work (task/milestone), reusing existing planning primitives rather than inventing a new one.

## Existing IMPLEMENTATION_PLAN.md Backlog

There is already a human-readable backlog/pending-candidate concept in IMPLEMENTATION_PLAN.md. Do not create two competing sources of truth — determine whether the new structured backlog should become authoritative and how IMPLEMENTATION_PLAN.md stays reconciled.

## Agent Usage

An agent should be able to record "found something out of scope" as deferred work rather than modifying unrelated files, then continue its current task.

## State and Lifecycle

Minimal lifecycle: pending -> promoted | archived. Invalid transitions rejected.

## Git Safety

Backlog operations must not unexpectedly modify user project files; only PitWay-managed state per existing write-scope rules. No automatic commits unless already an established PitWay convention for the relevant operation.

## Testing Requirements

Creation (required fields, stable id, source context, invalid input); listing/inspection; lifecycle (promote/archive/invalid transitions/repeats); traceability (source preserved, promotion preserves origin); state/journal (persistence, journal event generation, restart/reload); scope safety (no unrelated file/task/milestone mutation); reconciliation after normal/interrupted execution and resume.

## Documentation

What backlog/deferred work means, when to use it, how it differs from current task work, how to create/view/promote/archive, source traceability, relation to IMPLEMENTATION_PLAN.md.

## Non-Goals

Not a GitHub Issues/Jira replacement, not a PM system, not a remote issue tracker, no team collaboration backend, no AI issue classification, no notifications, no web UI, no cloud sync.

## Definition of Done

Existing architecture reviewed first; single authoritative backlog model; create/list/show/promote/archive implemented; source context preserved; lifecycle validated; promotion preserves origin; journal/state integration implemented; reconciliation covered; current task/milestone scope cannot be silently expanded; tests cover critical paths; existing tests remain green; coverage does not regress below established thresholds; documentation updated; IMPLEMENTATION_PLAN.md reflects final architecture/status; dogfooded on PitWay itself where practical.

## Implementation Discipline

Do not over-engineer. Prefer existing PitWay primitives over new abstractions, new states, or new files/subsystems where one already fits.
