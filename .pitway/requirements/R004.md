# M031 — PitWay Official Website

## Objective

Build the official PitWay website as a production-ready static marketing and documentation website.

The website should clearly explain what PitWay is, why it exists, how its controlled workflow works, and how developers can get started.

The website should also serve as a real-world example of PitWay's own workflow and development philosophy.

---

## Product Identity

### Product

**PitWay — The pit crew for agentic coding.**

### Tagline

**A controlled workflow for agentic software development.**

### Core Message

**Control the workflow, not the agent.**

The website should communicate that PitWay is designed to balance:

- The speed and automation of AI coding agents
- Human control over scope, requirements, verification, and important decisions

---

# Repository Structure

The website must live inside the existing PitWay repository.

Do not create a separate repository.

The website should be isolated under:

```text
website/
````

The existing PitWay CLI, source code, tests, and functionality must not be unnecessarily modified.

---

# Dependency Isolation

The website must be an independent npm project.

Expected structure:

```text
pitway/
├── package.json
├── src/
├── tests/
└── website/
    ├── package.json
    ├── content/
    ├── data/
    ├── diagrams/
    └── ...
```

Requirements:

* Website-specific dependencies must be declared in `website/package.json`.
* Website-only dependencies must not be added to the root `package.json`.
* `website/` must not be an npm workspace member.
* The website must be independently installable and buildable.
* Installing/running the PitWay CLI must not require website-only dependencies.
* Root `package.json` must remain focused on PitWay CLI dependencies.
* Avoid unnecessary dependency duplication.
* Only place a dependency at the root if it is genuinely shared by both the CLI and website.

The dependency boundary must be objectively verifiable.

---

# Content Architecture

Website content should be separated from presentation code.

## Markdown

Use Markdown for human-readable content such as:

* Documentation
* Concepts

Example:

```text
website/content/
├── pages/
├── concepts/
├── workflow/
└── getting-started/
```

Markdown must be converted to HTML at build time.

Do not render Markdown in the browser at runtime.

---

## Structured Data

Use YAML or another appropriate structured format for genuinely structured/repeated data such as:

* Navigation
* Feature lists
* Metadata
* Version information
* Structured page configuration

Prefer YAML over JSON when the data is primarily maintained by humans.

Do not use JSON unless there is a concrete reason.

# Mermaid Diagrams

Existing canonical Mermaid diagrams must be reused whenever possible.

Before creating a new `.mmd` file, inspect the repository for existing Mermaid sources.

If an existing Mermaid source represents the same PitWay workflow, concept, or behavior:

* Reuse the existing Mermaid source.
* Do not duplicate it into `website/diagrams/`.
* Treat the existing Mermaid source as the canonical source.
* Consume/reference it from the website build.
* Do not maintain two independent Mermaid sources for the same workflow.

Create a new `.mmd` file only when no suitable existing source exists.

If the website needs presentation-specific changes, prefer applying them through the build/rendering layer rather than duplicating the canonical Mermaid source.

---

# Mermaid Rendering

Mermaid diagrams must be rendered at build time.

```text
.mmd
  ↓
Mermaid renderer
  ↓
SVG
  ↓
Static website
```

Requirements:

* `.mmd` must be converted to SVG during the build.
* Mermaid must not be required at runtime in the browser.
* Do not load Mermaid from a CDN.
* Generated SVGs must have transparent backgrounds.
* Do not include an opaque background rectangle.
* SVG output must remain responsive and sharp.
* SVGs must work as normal static assets.

---

# Mermaid Color Requirements

Mermaid diagrams may be reused in multiple environments.

Therefore the canonical `.mmd` colors must be readable on both:

### PitWay Website

```text
#111629
```

### npmjs.org / Light Background

```text
#FFFFFF
```

The Mermaid color scheme must not be dark-only or light-only.

Colors should provide sufficient contrast on both backgrounds.

The diagrams should maintain the PitWay visual identity while remaining readable in both environments.

Approximate PitWay visual colors:

```text
Dark background:  #111629
Accent:           #64B8F7
Primary text:     off-white
Secondary text:   muted blue-gray
```

However, accessibility and cross-background readability take priority over exact brand-color matching.

The generated SVG background must remain transparent.

# Multi-Agent Resume

This is a key PitWay feature and should be prominently documented.

Example workflow:

```text
OpenCode
   ↓
stop
   ↓
Claude Code
   ↓
pitway resume
   ↓
continue
```

The website should communicate:

> The agent can change. The workflow doesn't have to.

The workflow state should allow another supported coding agent to continue from the existing PitWay state without requiring the developer to manually reconstruct the entire workflow.

Do not make unsupported claims about AI context or token retention.

Describe only what PitWay actually persists and resumes.

# Milestone Planning Requirements

The Milestone should be decomposed into a small number of focused tasks.

Each task must have:

* Objective
* Dependencies
* Explicit write scope
* Acceptance criteria
* Verification requirements

Avoid blanket write scopes such as:

```text
website/**
```

when they would subsume the write scope of later tasks.

Task-level write boundaries must remain meaningful and enforceable.
