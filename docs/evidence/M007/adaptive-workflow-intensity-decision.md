## The Adaptive Workflow Intensity decision

**Workflow tiers that exist after this milestone:**

1. **Milestone workflow** (unchanged) — full contract/task/verification ceremony, for substantive engineering work.
2. **Task-amendment / contract-amendment within a milestone** (M005, unchanged mechanically; AC002/AC004 add *documented guidance* on when to reach for it — never a new mechanism, never a weakened approval gate).
3. **One-task corrective milestone** (interim, effective now, per the AC005 post-completion refinement) — the supported path for any out-of-scope defect discovered outside an active milestone, until quick-change is built for real. Not a new mechanism — this is the existing milestone workflow, deliberately scoped to one task.
4. **Quick-change** (designed, deferred) — a future fourth tier for a specific, now-refined primary use case (post-milestone manual bug findings): create → one developer approval → journaled in-flight work → TDD/verification → one atomic commit with `PitWay-Change` → automatic completion. Promotes to a corrective milestone when it touches architecture, schema, public API, dependencies, security, migrations, multiple subsystems, or can't stay one atomic commit. Not built in this milestone.

**How a change is routed:** substantive new engineering work → milestone workflow. A small, in-scope-adjacent ripple fix discovered mid-task → AC004's folded-commit path (task-amend the write_scope first, then fix, per the developer's own added condition). A defect in already-completed tooling → AC007's recovery procedure, routed in-scope or deferred per its diagnose/route/fix/record steps. A defect or correction on a *specific already-completed task's deliverable* → AC008's completed-task-revision path (a new task in a subsequent milestone). Any other out-of-scope, non-milestone-shaped fix, right now → a one-task corrective milestone (interim), never an unattributed standalone commit. Once quick-change exists, that last case routes there instead, for its specific defined use case.

**What changes after this milestone:** the interim one-task-corrective-milestone policy is real and effective immediately. The established classification is preserved exactly, not collapsed into one number: **7 standalone recovery/hotfix commits across M005-M006** (M005: 4, M006: 3) — each a fix for a genuine defect in already-completed tooling — and, separately, **`85fa243`, one between-milestone maintenance commit** (no defect, no incident, a `.gitignore` normalization) that shares only the same underlying gap (no supported PitWay-attributed non-milestone path existed for either category). Going forward, that shared gap — not "the pattern" of either category individually — is addressed by the interim policy: any future out-of-scope defect fix uses a one-task corrective milestone rather than a further unattributed standalone hotfix commit; any future tiny, legitimate, non-milestone maintenance change is still handled ad hoc (as `85fa243` itself was) until quick-change exists for real, per its own now-refined design. The dispatch-mode rule (AC010) and the Decision Authority Policy (AC013) are both real, shipped, effective-now protocol changes governing how the driver executes future milestones' task graphs. Three items — quick-change, skills, structured-failure-extraction — carry a **roadmap/milestone-numbering impact whenever adopted**: none is assigned a specific milestone number now (each remains "a later, not-yet-numbered milestone," per their own AC text), a decision deliberately not pre-committed here.

**One item remains genuinely undecided, carried forward, not resolved by any M007 AC:** whether and how to build actual read-boundary enforcement (a worker reading outside its declared `context_files`) — M006/AC004's honesty boundary explicitly deferred this to "an M007 decision," but no M007 AC addressed it directly. **Explicit roadmap disposition (not resolved here, assigned to M008):** M008's own release-readiness contract must decide whether read enforcement is feasible and in scope for that milestone, or is instead formalized as an explicit non-goal — an advisory-only boundary, stated as such rather than left ambiguous. **Until that decision is made, no README or release claim may imply worker reads are technically enforced** — the honesty boundary already established (M006/AC004: PitWay bounds only the *supplied* bundle, never a subagent's total context or its actual reads) remains the accurate, current claim, and stays the accurate claim regardless of which way M008 ultimately decides.
